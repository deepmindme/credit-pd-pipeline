Задача и данные

  • Я в роли ML-инженера кредитного отдела: нужно автоматизировать разработку и обслуживание модели вероятности дефолта (PD).
  • Решение должно быть воспроизводимым, тестируемым и готовым к развёртыванию.
  • Датасет UCI Default of Credit Card Clients: 30 000 клиентов тайваньского банка, апрель–сентябрь 2005.
  • 23 признака: лимит, демография, статусы платежей, суммы счетов и платежей за 6 месяцев.
  • Таргет: дефолт в октябре. Таких клиентов 22%.

Архитектура пайплайна

validateGreat Expectations, 78 правил; при нарушении пайплайн стоп
→
prepareтипы, дубликаты, стратифицированный сплит 80/20
→
train6 экспериментов, CV-поиск, порог, MLflow + Registry
→
evaluateметрики, графики, gains-таблица, эталон для PSI
DVC — dvc.yaml описывает стадии, данные и модели версионируются, remote — ветка dvc-storage по HTTP
MLflow — параметры, метрики, артефакты, модели, датасеты; вложенные runs поиска
FastAPI + Docker — /predict, /predict/batch, /health; лёгкий образ для инференса
Мониторинг — поток заявок в API, PSI по скорам и 23 признакам, гейт --fail-on-drift
CI/CD — black, flake8, GE-валидация, 81 тест, dvc status, сборка образа, smoke-тест

Главное решение: очистка категорий и feature engineering живут внутри sklearn Pipeline, поэтому API принимает исходные 23 поля, а train/serve skew исключён.

Данные: EDA и валидация

  • Пропусков нет, но есть 35 дубликатов без учёта ID. Удаляю, чтобы не было утечки между train и test.
  • Недокументированные коды: EDUCATION 0/5/6, MARRIAGE 0. В suite они разрешены, в модели сведены к «другое».
  • Самый сильный сигнал — история просрочек PAY_x. Сырые суммы счетов почти бесполезны (IV ≈ 0.01).

Great Expectations suite (78 правил):

  • состав колонок, null, типы, уникальность ID;
  • коды категорий, диапазоны (возраст 18–100, платежи ≥ 0);
  • таргет ∈ {0, 1}, доля дефолтов 5–50%.

CLI возвращает код 1 при нарушении. В тестах проверены 14 видов аномалий, и отдельный тест падает, если аномалии появятся в реальной выгрузке.

DVC и CI/CD

$ dvc repro
validate → prepare → train → evaluate

$ dvc metrics show
reports/metrics.json  roc_auc 0.7794  gini 0.5587
                      f1 0.5363  threshold 0.2767
  • Под DVC: датасет, train/test, модель, эталон для PSI.
  • Remote — ветка dvc-storage по HTTP: dvc pull без ключей.
  • Параметры собраны в params.yaml.

GitHub Actions, на каждый push:

  • lint: black, flake8;
  • test: dvc pull → валидация GE → 81 тест pytest;
  • dvc: dvc.lock соответствует коду, стадии воспроизводятся байт в байт;
  • docker: сборка образа, запуск, smoke-тест /predict, мониторинг PSI.

REST API и Docker

$ ./scripts/docker_build_run.sh   # сборка, запуск, проверка /health

$ curl -X POST localhost:8000/predict \
    -H "Content-Type: application/json" \
    -d @scripts/sample_request.json
{"default_prediction": 1,
 "default_probability": 0.621562,
 "threshold": 0.276678}
  • POST /predict: клиент → класс и PD.
  • POST /predict/batch: до 1000 клиентов.
  • GET /health: версия модели и порог.
  • Pydantic-схема повторяет правила GE: возраст 12 или PAY_0 = 11 → 422.
  • Образ python:3.11-slim только с зависимостями инференса, без root, с HEALTHCHECK.
  • Без модели сервис не падает: /health и /predict отвечают 503.
  • Проверено локально (контейнер healthy, ответ выше) и в CI на каждый push.

Итоги и что дальше

Сделано

  • Воспроизводимый пайплайн одной командой dvc repro.
  • Данные проверяются до обучения и в каждом CI-прогоне.
  • 6 экспериментов в MLflow; модель откалибрована, ROC-AUC 0.779.
  • API в Docker, 81 тест, мониторинг дрифта с гейтом.

Что улучшить

  • Подбирать порог по стоимости ошибок, а не по F1.
  • Убрать пол из признаков (требования недискриминации).
  • Вынести MLflow на сервер, DVC remote — в S3.
  • Out-of-time валидация на данных за другие периоды.
  • Перейти на hist_gb_fe: то же качество в 12 раз быстрее.
